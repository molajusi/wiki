## 1. 개요 및 목적
*Overview & Purpose*

이 기획은 두 개의 산출물을 하나의 코드베이스로 동시에 만족시키려 합니다.

1. **본 게임(Playable Game)**: 픽셀 도트 아트의 플랫폼 기반 메트로이드배니아. 능력 획득에 따른 맵 게이팅과 탐험이 실제로 작동하는 완결된 플레이 경험.
2. **연출 라이브러리/API(Cinematic Direction Layer)**: 게임 로직과 분리된 계층으로, "이 캐릭터가 이 감정을 지으며 이 대사를 이 카메라 구도에서 말한다"는 연출 단위를 데이터로 기술·재생·녹화할 수 있는 재사용 가능한 인터페이스. 이 계층이 쇼츠 영상 제작의 실질적 핵심이며, 동시에 게임 본편의 컷신·NPC 대화에도 그대로 사용됩니다.

목적은 두 산출물을 분리 개발하지 않고, **연출 이벤트를 게임 상태와 동일한 데이터 모델로 다뤄 한쪽에서 만든 연출 자산이 다른 쪽에서도 그대로 재생되도록** 만드는 데 있습니다. 이렇게 설계하면 쇼츠용으로 만든 장면이 나중에 게임 본편의 컷신으로 재사용되고, 반대로 게임 플레이 중 만들어진 상황도 별도 작업 없이 쇼츠용으로 재녹화할 수 있습니다.

<div class="callout">
<strong>1차 평가에서 확정된 방향 전환</strong>: 최초 브리핑에서는 "쇼츠 연출용 무대"가 목적이고 메트로이드배니아는 장르적 외피에 가까웠으나, 아저씨가 "플레이 가능하고, 이후 이를 기반으로 게임도 만들고 싶다"고 명시하면서 메트로이드배니아의 능력 게이팅·탐험 시스템도 더 이상 선택적 요소가 아니라 <b>정식 설계 대상</b>이 되었습니다. 이에 따라 이전 평가에서 "게이팅 밸런스는 후순위"라 했던 판단은 이 문서에서 철회합니다.

## 2. 핵심 개념 및 원리 — 이중 목적 아키텍처
*Core Concepts — The Dual-Purpose Architecture*

### 2.1 연출 이벤트를 게임 상태의 일부로 모델링

핵심 설계 원칙은 "연출은 게임과 별도로 스크립팅되는 컷신이 아니라, 게임이 이미 다루는 상태(캐릭터 위치, 감정, 대사, 카메라)를 시간 축 위에 기록·재생하는 것"이라는 관점입니다. 이렇게 하면 연출 라이브러리가 게임 엔진 위에 얹힌 부가 기능이 아니라, 게임 자체의 상태 직렬화(state serialization) 메커니즘을 재사용하는 형태가 됩니다.

```
[연출 라이브러리/API의 위치]

┌─────────────────────────────────────────────────────────┐
│                     게임 로직 (Game Logic)                │
│   플레이어 입력 → 물리/충돌 → 능력 게이팅 → 맵 상태 전이   │
└───────────────────────────┬─────────────────────────────┘
                             │ 공유 상태 모델
                             │ (위치, 애니메이션 상태, 감정 태그, 대사 큐)
┌───────────────────────────▼─────────────────────────────┐
│              연출 라이브러리/API (Cinematic Layer)         │
│  - 타임라인 기록기(Recorder): 실제 플레이 중 상태 스냅샷 채집│
│  - 연출 스크립트 재생기(Player): 사전 작성된 연출 데이터 재생│
│  - 카메라 리그: 프레이밍/줌/트래킹을 독립 제어              │
│  - 대사풍선 렌더러: 화자·감정 태그에 따라 스타일 자동 결정  │
└───────────────────────────┬─────────────────────────────┘
                             │
              ┌──────────────┴──────────────┐
              ▼                              ▼
   [게임 내 실시간 표시]              [영상 파일로 익스포트]
   (본편 컷신, NPC 대화)              (쇼츠 녹화/재현용)
```

### 2.2 두 가지 진입 경로

- **레코더 경로**: 실제 플레이 세션 중 특정 구간을 타임라인으로 채집(캐릭터 좌표, 애니메이션 클립, 감정 태그, 대사 텍스트, 카메라 값)하여 이후 그대로 재생하거나 영상으로 뽑아냅니다. 우연히 나온 좋은 상황을 "재현 가능한 자산"으로 박제하는 경로입니다.
- **연출 스크립트 경로**: 실제 플레이 없이 연출 데이터를 직접 작성(또는 툴로 편집)해 특정 장면을 처음부터 연출합니다. 게임 본편의 고정 컷신은 이 경로로 만들어집니다.

두 경로가 동일한 데이터 스키마(캐릭터 ID, 좌표, 감정 태그, 대사, 카메라 파라미터의 시간축 배열)를 공유해야 위 1절의 목적("한쪽 자산이 다른 쪽에서도 재생됨")이 성립합니다. 이것이 이 아키텍처에서 가장 먼저 확정해야 할 기술적 결정입니다.

### 2.3 API로 노출할 것인가, 내부 라이브러리로만 둘 것인가

"라이브러리 혹은 API"라는 원 브리핑의 표현대로, 두 가지 노출 수준이 가능하며 우선순위가 다릅니다.

| 구분 | 내부 라이브러리 | 외부 API |
| :--- | :--- | :--- |
| 대상 | 게임 자체(본편 컷신 재생) | 외부 도구(별도 녹화 프로그램, 커뮤니티 제작 연출 등)에서 이 게임의 연출 엔진을 호출 |
| 구현 비용 | 낮음(게임 내부 모듈) | 높음(직렬화 포맷 고정, 버전 호환, 문서화, 보안/샌드박싱 필요) |
| 이 시점의 판단 | **우선 이것부터** | 게임과 연출 레이어의 데이터 스키마가 안정화된 이후 2단계 과제 |

내부 라이브러리 수준의 완성도를 먼저 확보하고, 외부 API 공개는 스키마가 안정된 다음 단계로 미루는 것을 권장합니다. 처음부터 외부 공개용 API로 설계하면 스키마 변경 비용이 커져 초기 반복 속도가 떨어집니다.

### 2.4 연출 스크립트 데이터 포맷

2.2절의 두 진입 경로를 실제로 구현할 데이터 포맷을 구상했습니다. Godot을 이미 채택했으므로(5장), 그 채택 근거(텍스트 기반 `.tres`, 에이전트 협업 적합도)를 살리는 방향으로 설계하되, 검토 과정에서 원안의 결함을 발견해 수정했습니다.

#### 2.4.1 연출 데이터와 게임 로직의 분리 — 리소스 이원화

원안은 7.3절의 규칙 세트 플래그(즉사 판정 등 게임플레이 로직)를 연출 리소스 안에 함께 넣었으나, 이는 2.1절에서 정한 "연출 라이브러리는 게임 로직과 분리된 계층"이라는 원칙과 충돌합니다. 이를 바로잡아 리소스를 둘로 나눕니다.

- **`CinematicSequence`**: 순수 연출 데이터(무엇이 보이고 들리는가) — 캐릭터 위치·애니메이션, 감정 태그(4장), 대사, 카메라 파라미터(2.1절), 하이라이트 트림 마커(7.4.3절), 연출 가능 순간/챕터명(7.4.4·7.5.3절), 가로/세로 프레이밍 프로파일(7.4.2·7.5.2절).
- **`SequenceModeConfig`**: 순수 게임 로직 데이터(무엇이 판정되는가) — 7.3절의 규칙 세트 A/B/C 플래그 조합, 탐지 판정 수치.
- 시퀀스 진입 시 두 리소스를 함께 참조만 하며, 서로의 내부를 알 필요가 없습니다.

#### 2.4.2 두 진입 경로에 서로 다른 포맷을 매핑

커스텀 이벤트 배열 하나로 두 경로를 통일하려 했던 원안을 재검토한 결과, 각 경로의 실제 용도에 맞춰 포맷을 이원화하는 것이 더 현실적이라는 결론에 이르렀습니다.

| 경로 | 포맷 | 근거 |
| :--- | :--- | :--- |
| 연출 스크립트 경로(사람이 정교하게 다듬는 컷신) | Godot 네이티브 `AnimationPlayer`/`Animation` | 내장 시각적 타임라인 에디터로 스크럽·드래그 편집 가능. 메서드 트랙(`set_emotion_tag()`, `show_dialogue()` 등)으로 특정 시점에 함수 호출. 캐릭터별 트랙을 여러 개 두면 동시다발 이벤트도 자연스럽게 표현됨. |
| 레코더 경로(플레이 중 자동 채집) | 커스텀 경량 `CinematicSequence` Resource(단순 이벤트 배열) | 프로그램이 생성·파싱하기 쉬운 단순 구조가 유리하고, 사람이 직접 읽을 일이 적어 시각적 에디터의 이점이 크지 않음. |

`Animation` 리소스는 키프레임이 패킹된 float 배열로 저장돼 원안의 커스텀 스키마보다 에이전트가 직접 손편집하기는 불편하다는 점을 트레이드오프로 인지하고 있습니다 — 다만 이 포맷은 사람이 Godot 에디터로 직접 다듬는 것을 전제하므로, 에이전트 편집 편의성보다 시각적 저작 편의성이 우선하는 경로입니다. `CinematicPlayer` 노드가 두 포맷을 공통 런타임 인터페이스로 추상화해 재생합니다.

#### 2.4.3 다국어 대사 — 로컬라이제이션 키 저장

대사 필드에 원문 텍스트를 직접 저장하면 4.3절의 "다국어 지원 여부" 오픈 이슈가 그대로 남습니다. 대신 Godot 자체 로컬라이제이션 시스템(CSV/PO 임포트)의 **키**를 저장하고, 실제 텍스트는 번역 테이블에서 가져오는 방식으로 설계합니다. 이렇게 하면 다국어 지원이 연출 데이터 설계와 동시에 자연스럽게 해결됩니다.

#### 2.4.4 레코더 경로는 델타 인코딩

"매 프레임 상태를 채집"하면 60fps 기준 이벤트 배열이 순식간에 비대해집니다. 상태가 실제로 바뀐 시점에만 이벤트를 기록하는 **델타 인코딩**으로 수정합니다(예: 감정 태그가 바뀔 때, 대사가 새로 시작될 때, 카메라 목표가 바뀔 때만 기록).

<p><strong>범위 표시</strong>: 이 절은 리소스 이원화·포맷 매핑·로컬라이제이션 키·델타 인코딩이라는 방향만 정리했습니다. `CinematicSequence`/`SequenceModeConfig`의 정확한 필드 스키마, `Animation` 트랙과 메서드 이름의 구체적 명세, `CinematicPlayer`의 추상화 인터페이스 세부 설계는 아직 이루어지지 않았습니다. 포맷 버저닝(필드 추가·삭제 시 하위호환)은 시퀀스가 아직 쌓이지 않은 현재 단계에서는 과잉설계로 판단해 다루지 않았습니다. 이 모두를 8장 오픈 이슈로 남겨둡니다.</p>

## 3. 세계관 및 정치 체제 설계 — 연출 레이어와 게임 레이어의 분리
*Worldbuilding: Divergent Political Systems Between the Cinematic Layer and the Game Layer*

### 3.1 시대 분위기와 이 위키의 기존 고려풍 세계관과의 관계

세계관은 마법(주술·도술)과 냉병기(칼·창·활)가 공존하는 중세 고려시대풍 가상 판타지입니다. 실제 고려사를 배경으로 삼지 않고 질감만 차용하는 방식은, 이 위키에 이미 존재하는 `goryeo_horizontal_fantasy_worldbuilding.html`의 2.1절 "고전풍 공화주의와 미학·체제의 분리" 원칙과 방법론적으로 동일합니다. 다만 이 기획은 정치 체제를 **게임 레이어(공화체제로 고정)와 연출 레이어(체제에 구애받지 않는 자유 소재)로 분리**해 다룹니다.

<div class="callout">
<p><strong>연출 레이어는 정치 체제에 고정되지 않는 범용 무대</strong>: 연출 레이어(쇼츠/지식영상)는 신분제 하나에 묶이지 않습니다. 다룰 수 있는 소재는 최소 세 갈래입니다 — ① <b>현실 역사</b>(신분제 사회를 포함한 임의의 시대), ② <b>게임이 실제로 채택한 공화체제 세계 그 자체</b>, ③ <b>그 공화체제 세계 안팎에 존재할 수 있는 왕정적 소재</b>(예: 공화정 수립 이전의 역사, 국경 너머 이웃 왕국, 몰락한 옛 왕조 등). 게임의 정식 세계관이 공화체제라 해도, 연출 레이어는 그 세계의 과거나 주변국으로 왕정을 얼마든지 무대에 올릴 수 있습니다.</p>
<p>이렇게 설계하는 이유는 연출 라이브러리/API가 특정 한 편의 영상 전용 도구가 아니라, 임의의 시대·체제·인물 구성을 기록·재생할 수 있는 범용 세트 라이브러리(2장 아키텍처)이기 때문입니다. 3.2절의 6단 신분 계층 구조는 그 다양한 소재 중 <b>신분제를 다룰 때 쓰는 데이터셋 하나</b>일 뿐이며, 연출 레이어가 항상 따라야 하는 고정 설정은 아닙니다.</p>
<p>반면 <b>플레이어블 게임 본편</b>이 실제로 진행되는 정식 세계·정치 체제는 여전히 <b>공화체제 하나로 고정</b>합니다. 게임 시스템(세력 관계, 진행 동기, 능력 게이팅의 서사적 근거)이 여러 체제를 동시에 지원하도록 설계하면 범위가 지나치게 커지므로, 게임 자체의 정치 체제는 단일하게 유지하는 편이 합리적입니다. 이 점에서 게임 레이어는 <code>goryeo_horizontal_fantasy_worldbuilding.html</code>의 "혈통 군주정 거부" 노선과 방향은 같아지지만, 그 문서와 세계관을 공유하는 것은 아니며 이 프로젝트만의 별도 공화체제입니다.</p>
<p>정리하면: <b>게임 레이어는 공화체제로 고정, 연출 레이어는 체제 무관하게 자유</b>입니다. 연출 레이어가 다루는 왕정 소재(신분제 사회 등)가 게임 세계의 과거사로 시간적으로 연결되는지, 완전히 별개의 역사·세계선으로 다뤄지는지는 아직 미확정이며 다음 단계에서 결정이 필요한 항목입니다.</p>
</div>

### 3.2 6단 신분 계층 구성(연출 레이어가 다루는 신분제 소재 데이터셋 예시, 1차 정의, 세부 미확정)

| 계층 | 호칭 | 비고(에이전트 해석, 확정 아님) |
| :--- | :--- | :--- |
| 왕 | **왕(王)** | 국가 최고 권위. 등장 빈도·직접 조작 가능 여부 미정. |

### 3.2.1 지방세력가의 역사적 원형(요약)

"지방세력가"는 고려 호족(豪族) — 정확히는 그 후예 중 개경 진출에 실패하고 지방에 남아 세습적 지배층이 된 계열(제도명 **호장 戶長**/향리 鄕吏) — 에 대응합니다. 이들은 귀족은 아니되 사유지·지방민의 존숭·과거 응시 자격 등 실질적 특권을 누렸고, 성종 2년(983) 이후 중앙에서 파견된 목사(牧使) 등 외관과 구조적으로 긴장 관계에 있었습니다. 다만 "호족"이라는 단어 자체는 1차 사료(삼국사기·고려사)에 없는 현대 학계의 소급 조어이며, 사료상의 실제 용어는 시기에 따라 성주(城主)·장군(將軍, 건국 전후) 또는 호장·향리(제도화 이후)로 갈립니다. 유럽식 "영주"와의 동일시도 학계에서는 신중히 다뤄집니다.

상세 근거·용어 논쟁·시기별 호칭 비교표는 별도 문서 [고려 호족·향리와 지방세력가 호칭 고증](goryeo_hojok_hyangni_terminology.html)으로 분리했습니다.

### 3.3 마법 체계 재사용 검토

`goryeo_horizontal_fantasy_worldbuilding.html` 5장에는 이미 "통합 도술 체계"(공학·염원·대가 3대 원동력, 목화토금수 오행 4대 원소 변환술)가 설계되어 있습니다. 신분 구조는 다르지만 마법 체계 자체는 세계관 공유 자산으로 재사용하거나 변형해 쓰는 편이 처음부터 새로 설계하는 것보다 효율적입니다. 이 기획에서 별도 마법 체계를 새로 만들 필요가 있는지, 위 체계를 차용할지는 아직 결정되지 않았습니다.

## 4. 캐릭터 감정표현 및 대사풍선 시스템
*Character Expression and Speech Bubble System*

이 두 항목이 쇼츠 연출의 실질적 본체이므로, 게이팅·전투 시스템보다 먼저 프로토타이핑 우선순위를 가져야 합니다.

### 4.1 감정표현 구현 방식의 선택지

- **스프라이트 단독 표현**: 도트 해상도 안에서 표정을 직접 그림. 표현 폭이 좁고 프레임 수가 많이 필요.
- **과장 기호 이펙트**: 땀방울, 분노 혈관, 반짝임, 물음표 등 만화적 기호를 감정 태그에 따라 자동 배치. 구현이 가장 가볍고 도트 스타일과 궁합이 좋음.

두 방식은 상호 배타적이지 않으며, 2장의 "감정 태그" 데이터 모델에 여러 표현 계층(스프라이트 포즈 + 기호 이펙트)을 동시에 연결하는 조합 설계가 가능합니다.

<p><strong>현재 채택하지 않음 — 초상화 인셋 병행</strong>: 대사풍선 옆이나 화면 구석에 별도 초상화(버스트) 스프라이트를 두어 표정을 전담시키는 방식은 매력적이나, 스프라이트 포즈와는 별개로 초상화 전용 그림을 감정 태그·신분 계층별로 꾸준히 제작해야 해 작화 리소스 부담이 큽니다. 지금은 이를 전담할 작업자가 없어 <b>채택하지 않기로 결정</b>했습니다. 인력이 확보되면 2장의 "감정 태그" 데이터 모델에 세 번째 표현 계층으로 다시 추가할 수 있도록, 폐기가 아니라 보류로 남겨둡니다.</p>

### 4.2 대사풍선 렌더러

"무대에서 바로 대사풍선으로 보여준다"는 요구는 화면 밖 UI 레이어(하단 텍스트박스 등)가 아니라 **캐릭터 머리 위 월드 스페이스 풍선**을 의미하는 것으로 해석됩니다. 이 경우:

- 풍선 위치가 카메라 프레이밍과 충돌하지 않아야 하므로, 카메라 리그(2.1절 아키텍처의 카메라 리그)와 풍선 배치 로직이 서로의 상태를 참조해야 합니다.
- 감정 태그에 따라 풍선 형태(테두리 삐죽삐죽=분노, 점선=속삭임, 물결=떨림 등)를 자동 변형하면 4.1절의 감정표현 이펙트와 시각적으로 중복되지 않게 역할을 나눌 수 있습니다(몸짓=포즈/기호, 말투=풍선 형태).

### 4.3 확정이 필요한 항목

- 감정 태그의 분류 체계(예: 기쁨/분노/슬픔/놀람/경멸 등 몇 종을 1차로 지원할지)
- 대사풍선이 다국어(한국어/영어 등) 텍스트를 다룰지, 세로쓰기 등 시대극 감성의 서체 연출을 넣을지(다국어 지원 자체는 2.4.3절의 로컬라이제이션 키 저장 방식으로 데이터 구조상 해소됨 — 서체 연출 여부는 여전히 미정)

## 5. 기술 스택 결정 — Godot 엔진 채택
*Technology Stack Decision — Adopting the Godot Engine*

### 5.1 비교 후보와 판단 기준

아저씨와의 논의에서 "이 프로젝트를 저(에이전트)와 함께 구현하는 데 적합한가"를 1차 기준으로 삼아 무료 2D 게임엔진을 비교했습니다. 판단 기준은 다음 네 가지였습니다: ① 프로젝트 파일이 텍스트 기반이라 에이전트가 직접 읽고 편집할 수 있는가, ② CLI/헤드리스 실행으로 자동화가 가능한가, ③ 룸(타일맵) 디자인 도구가 얼마나 통합되어 있는가, ④ 커뮤니티/자료 규모.

| 후보 | 비교 결과 |
| :--- | :--- |
| **Godot** | `.tscn`/`.tres`가 텍스트 기반, CLI 헤드리스 지원, `TileSet`/`TileMap` 내장 에디터로 룸디자인이 엔진 하나로 완결. 커뮤니티 최대. |
| **LÖVE (Love2D)** | 프로젝트가 100% 코드라 에이전트 협업 적합도는 이론상 가장 높음. 다만 내장 에디터가 없어 룸디자인은 별도 툴 Tiled + 로더 라이브러리(STI) 조합이 필요. |
| **Defold** | Godot·LÖVE와 마찬가지로 텍스트 기반 프로젝트에 CLI 빌드 지원. 다만 세 후보 중 커뮤니티·자료가 가장 작음. |

### 5.2 제외 및 채택 경위

1. **Defold 제외**: 아저씨가 "커뮤니티가 Godot보다도 작다면 피하고 싶다"고 명시해, 세 후보 중 커뮤니티 규모가 가장 작은 Defold을 1차로 제외했습니다.
2. **Godot vs LÖVE 비교**: 에이전트 협업 적합도만 보면 LÖVE가 이론적으로 우위이나(에디터 자체가 없어 프로젝트 전체가 코드), 아저씨가 "룸디자인·타일맵에 전혀 감이 없다"고 밝힌 상태에서는 LÖVE의 Tiled+STI 외부 툴 조합이 실질적 진입장벽으로 작용한다고 판단했습니다. 반면 Godot은 룸디자인 도구가 엔진에 내장되어 있어 툴 하나로 해결되고, 이 격차가 "Godot의 `.tscn`/`.tres`도 이미 텍스트 기반이라 LÖVE 대비 에이전트 협업 격차는 크지 않다"는 점과 합쳐져 Godot 쪽으로 저울이 기울었습니다.
3. **기존 친숙도**: 아저씨가 Godot을 "이미지로나마 이미 친숙해서 선호하고 싶다"고 밝힌 기존 선호와도 위 판단이 일치했습니다.

<div class="callout">
<strong>최종 결정</strong>: <b>Godot 엔진</b>을 이 프로젝트의 기술 스택으로 채택합니다. 결정 근거는 커뮤니티 규모가 아니라(그건 Defold 제외 사유였을 뿐), <b>룸디자인 도구의 엔진 내장 여부</b>가 최종 결정 요인이었습니다. 다만 Tiled는 Godot에서도 임포터 플러그인으로 쓸 수 있으므로, 내장 TileMap 에디터가 부족하다고 느껴지면 언제든 전환 가능한 대안으로 남겨둡니다.

### 6.3 스프라이트 아웃라인 기법 — 테두리 있는 도트와 없는 도트

전통적으로 도트 아트 캐릭터·오브젝트에 검은 테두리를 두르는 방식과, 테두리 없이 색상 대비만으로 형태를 표현하는 방식이 공존합니다. 픽셀 아트 실무 커뮤니티(원문: `raw/20260930_pixel_art_outline_technique_research_raw.txt`) 자료를 조사한 결과, 이는 이분법이 아니라 4가지로 세분됩니다.

| 기법 | 원리 | 인상 | 장단점 |
| :--- | :--- | :--- | :--- |
| **하드 블랙 아웃라인** | 오브젝트 전체를 순수 검은 선으로 완전히 둘러쌈 | 그래픽적·고대비, 다소 무겁고 만화/UI적 | 어떤 배경 위에서도 실루엣이 확실히 분리됨(스크롤 환경에 강함). 다만 시각적으로 무거움. |
| **아웃라인 없음** | 별도 테두리 없이 배경과의 색상 대비에만 의존 | 부드럽고 자연스러운 페인팅에 가까운 인상 | 배경이 복잡하거나 색이 겹치면 실루엣 구분이 어려워질 수 있음(작은 도트일수록 위험). |
| **선택적 아웃라인(Sel-Out)** | 배경과 맞닿는 그림자 쪽만 진한 선, 빛 받는 쪽은 밝은 내부색을 그대로 살려 흐리게 처리 | 정교하고 자연스러움 — "프로들이 기본으로 쓰는 방식" | 명도 대비를 유지하면서도 하드 블랙보다 세련됨. 배경색이 바뀔 때마다 재조정이 필요해 제작 난도는 가장 높음. |
| **색상 맞춤 아웃라인** | 순수 검은색 대신 칠해진 색과 같은 색상군의 더 어두운 톤을 테두리로 사용 | 하드 블랙보다 부드럽고 오브젝트 색과 조화로움 | 구현은 선택적 아웃라인보다 간단하나, 배경이 어두우면 명도 대비가 떨어질 수 있음. |

<div class="callout">
<p><strong>신뢰도 유의점</strong>: 위 4가지 분류와 원리는 픽셀 아트 실무 커뮤니티(Lospec, Pixnote, Pixel-Editor.com 등)의 튜토리얼 자료에서 공통적으로 확인되어 용어·원리 자체의 신뢰도는 높습니다. 다만 특정 게임(Shovel Knight, Owlboy, Celeste 등)이 정확히 어느 기법을 썼는지에 대한 검증된 기술 분석까지는 확보하지 못해, 6.1절의 "대표작" 열과 이 표의 기법을 1:1로 단정 짓지 않았습니다.</p>
</div>

이 프로젝트는 6.4절의 후처리 효과(특히 블룸)와 함께 쓰일 것을 감안하면, **선택적 아웃라인**이 가장 궁합이 좋습니다 — 하드 블랙 아웃라인은 빛번짐 효과와 시각적으로 충돌하기 쉽고(검은 선이 블룸의 부드러운 느낌을 깨뜨림), 아웃라인 없음은 3장에서 다양한 룸(세트)을 오가는 무대 특성상 배경이 계속 바뀌어 캐릭터 가독성이 떨어질 위험이 있습니다. 다만 선택적 아웃라인은 제작 난도가 가장 높으므로, 초기 프로토타입 단계에서는 **색상 맞춤 아웃라인**으로 시작해 리소스가 허락할 때 선택적 아웃라인으로 승격하는 단계적 접근을 권장합니다.

### 6.4 화면 후처리 효과 및 Godot 구현 경로

최근 인디 도트 게임의 "아련한" 느낌은 스프라이트 자체가 아니라 **화면 전체에 덧씌우는 후처리 레이어**에서 나옵니다. 핵심은 순서입니다 — 저해상도로 선명하게 그린 뒤, 확대 전후에 후처리를 별도 패스로 입혀야 도트가 뭉개지지 않습니다(2장 아키텍처의 "레이어 분리" 원칙과 같은 사고방식).

| 효과 | 원리 | Godot 구현 난이도 |
| :--- | :--- | :--- |
| 블룸(빛번짐) | 밝은 픽셀만 추출 → 블러 → 원본에 가산 합성 | **낮음 — 내장 기능**. `WorldEnvironment`의 `Environment` 리소스에서 Glow를 켜면 2D에도 바로 적용됨. |
| 색수차 | R/G/B 채널을 화면 중심에서 멀어질수록 다른 방향으로 어긋나게 샘플링 | 낮음 — 커스텀 `.gdshader` 10줄 안팎 |
| CRT/스캔라인 | 수평 줄무늬 + 가장자리 왜곡(배럴 디스토션) + 비네팅 | 낮음 — 커뮤니티에 검증된 템플릿 다수 |
| 물결/굴절 효과 | 시간에 따라 스크롤되는 노이즈 텍스처로 화면 UV를 흔들어 샘플링 | 중간 |
| 모션 블러 | 잔상 스프라이트 누적 또는 속도 버퍼 기반 블러 | 높음 — 우선순위 후순위 권장 |

구현 파이프라인은 ① `SubViewport`에 저해상도로 게임을 렌더링 → ② `TextureRect`(필터: Nearest)로 픽셀퍼펙트 출력 → ③ 그 위에 풀스크린 셰이더로 효과를 순서대로(블룸 → 색수차 → CRT → 물결굴절 → 모션블러) 얹는 구조를 권장합니다.

### 6.5 이 프로젝트 적용 권고

- 해상도/팔레트는 **16비트급(SNES/제네시스 급)으로 확정**(6.1절, 아저씨 확정).
- 아웃라인은 **색상 맞춤 아웃라인으로 시작해 선택적 아웃라인으로 단계적 승격**(6.3절).
- 후처리는 **블룸(내장, 즉시 적용 가능) → 색수차 → CRT 스캔라인 → 물결굴절 → 모션블러** 순으로 난이도가 낮은 것부터 단계적으로 도입할 것을 권장합니다(6.4절).

숨겨진 구역과 능력 획득 전에는 갈 수 없는 구역이라는 두 축은 이 위키의 기존 이론 문서에 이미 체계적으로 정리돼 있습니다: 능력 게이팅·백트래킹 루프는 `metroidvania_mechanics_and_level_design.html`, 게이팅의 설계 철학 일반은 `game_gating_mechanisms.html`을 참조합니다. 이 기획에서 별도로 재정의하지 않고 그대로 채택합니다. Moon Studios CEO 토마스 말러는 《오리 앤 더 윌 오브 더 위습스》 개발 인터뷰에서, 게이팅 설계 시 시퀀스 브레이킹(의도하지 않은 순서로 구역에 진입하는 것)을 막기 위해 물리 상호작용을 세심히 관리해야 했다고 밝혀, 게이팅이 "능력 체크 하나만 걸면 끝"이 아니라 물리 엔진 차원의 지속적 검증이 필요한 작업임을 보여줍니다. [[16]](#ref-16)

### 7.2 스크립트 시퀀스 모드 — 추격 시퀀스의 두 하위 유형

게임 디자인 매체 Game Developer(舊 Gamasutra)는 추격 시퀀스(Chase Sequence)를 "적이 플레이어를 추격한다는 사실과 대안 경로의 부재로부터 긴장감이 발생하는, 대체로 선형적인 레벨"로 정의합니다. [[17]](#ref-17) 이 기획에서는 그 안에서도 규칙이 정반대인 두 하위 유형을 구분합니다.

| 유형 | 핵심 규칙 | 근거·사례 | 플레이어의 유효 전략 |
| :--- | :--- | :--- | :--- |
| **연속 도주형** | 강제 전진/스크롤, 환경 접촉 즉사, 전투 비활성화, 정지는 곧 죽음 | 《슈퍼 메트로이드》 최종 탈출 시퀀스 — 마더 브레인 격파 후 행성 자폭까지 벽·바닥이 무너지고 사운드트랙이 공포로 전환되는 환경 연출로 긴장을 조성 [[18]](#ref-18) | 계속 움직이며 정확한 타이밍의 점프·대시만 유효 |
| **시선 회피형** | 탐지(시야콘) 판정, 은신 가능 구역 존재, 정지·대기가 유효한 전략 | 시야콘(Vision Cone) 메커닉은 1981년 세가의 《005》가 최초 도입(기네스 세계기록 공인 "최초의 스텔스 게임") [[19]](#ref-19). 《리틀 나이트메어》 시리즈의 거대 추격자(선생님, 쌍둥이 요리사 등) 회피 구간이 실제 구현 사례 [[20]](#ref-20) | 위협의 시야 패턴을 읽고 멈추거나 숨는 판단이 핵심 |

두 유형은 리듬이 정반대입니다(도주형은 "멈추면 죽음", 회피형은 "멈추는 게 전략") — 하나의 규칙으로 뭉뚱그려 설계하면 안 됩니다.

### 7.2.1 사례 연구 — 《오리 앤 더 블라인드 포레스트》의 쿠로 시퀀스

아저씨가 처음 언급한 거대 부엉이 쿠로(Kuro) 시퀀스를 별도로 재조사했습니다(원문: `raw/20260930_chase_sequence_level_design_research_raw.txt` 1-7·1-9절). 쿠로는 오리가 태어날 때 정령나무가 방출한 빛이 자신의 새끼를 모두 죽인 사건의 피해자로 설정되어 숲을 파괴하며 오리를 적대시하는 서사적 동기를 갖습니다. [[21]](#ref-21) 게임 내 관련 시퀀스는 하나가 아니라 **최소 세 개**이며, 이들을 비교하면 규칙 세트 A·B의 관계에 대한 중요한 시사점이 나옵니다.

| 시퀀스 | 규칙 | 세부 진행 |
| :--- | :--- | :--- |
| 긴소나무(Ginso Tree) 탈출("물 탈출") | **순수 규칙 세트 A(연속 도주형)** | 물의 원소를 되살리면 나무 내부에 홍수가 차오름 → 랜턴·적·투사체를 연달아 bash하며 상승, 이중 점프·벽점프로 만회 → 정상 도달 직후 쿠로가 나타나 오리를 떨어뜨림. 물은 정속이 아니라 **플레이어가 느리게 움직이면 함께 느려지는 적응형 페이싱**. [[32]](#ref-32)[[33]](#ref-33)[[34]](#ref-34) |
| 중반부 폐허 탈출 | **순수 규칙 세트 B(시선 회피형)** | 얼음을 깨고 물속에 숨음 → 나무 뒤에 숨음 → 쓰러진 통나무 밑에 숨어 밀며 이동(엄폐물 겸 이동 수단) → 뛰쳐나가 도주 → 바위가 굴러떨어져 쿠로를 가로막으며 종료. 쿠로 시야에 오래 노출되면 즉사. [[22]](#ref-22)[[23]](#ref-23)[[24]](#ref-24) |
| 후반부 마운트 호루 탈출(엔딩 직전) | **규칙 세트 A + B 중첩** | 화산 불길이 번지는 가운데, 불타는 나뭇가지 위를 활공하거나(낙하가 더 빠를 땐 일부러 떨어짐) 물속에서 물고기 떼를 들이받으며 전진해야 하는 연속 도주형 규칙에, "쿠로 시야에 오래 노출되면 즉사"라는 시선 회피형 규칙이 동시에 겹쳐 적용됨. [[21]](#ref-21) |

긴소나무 탈출은 정상 도달 직후 쿠로가 개입해 끝나므로, 쿠로의 즉사 시야 판정이 섞이지 않은 **가장 전형적인 규칙 세트 A 단독 사례**입니다 — 마운트 호루(A+B 중첩)보다 순수한 대조군으로 쓸 수 있습니다.

<div class="callout">
<p><strong>아키텍처 시사점</strong>: 마운트 호루 시퀀스는 규칙 세트 A와 B가 상호 배타적이지 않고 <b>한 시퀀스 안에서 레이어처럼 중첩 적용될 수 있음</b>을 보여주는 실제 사례입니다. 따라서 7.3절의 "규칙 세트 플러그인" 아키텍처는 시퀀스당 세트 하나만 선택하는 단일 선택(enum)이 아니라, <b>여러 세트를 동시에 켤 수 있는 플래그 조합(비트마스크 등)</b>으로 설계하는 것이 실제 요구에 더 부합합니다.</p>
</div>

**반면교사 — 트라이얼 앤 에러 비판**: 쿠로 시퀀스는 Steam 커뮤니티·ResetEra·NeoGAF·ExLudico 리뷰 등 다수 독립 출처에서 일관되게 "예고 없는 즉사 함정이 많아 최소 한 번은 죽어봐야 회피법을 알 수 있고, 세이브 포인트가 없어 실패 시 시퀀스 전체를 다시 해야 한다"는 비판을 받았습니다(반론도 존재하나 비판이 다수). [[25]](#ref-25)[[26]](#ref-26)[[27]](#ref-27) 이는 앞서 인용한 Game Developer의 "프리뷰 기법"(위협을 접하기 전 환경을 미리 보여주는 원칙)을 지키지 못했을 때 생기는 결과를 보여주는 반면교사 사례입니다. 이 기획에서는 ① 예고 없는 즉사 함정을 배치하지 않고, ② 시퀀스 내부에 구간별 체크포인트를 두어 실패 시 처음부터 반복하지 않게 하는 두 원칙을 규칙 세트 A·B 공통 설계 지침으로 채택합니다.

### 7.2.2 사례 연구 — 《오리 앤 더 윌 오브 더 위습스》의 슈리크 시퀀스

슈리크는 부패(the Decay)의 영향으로 몸에 돌 층이 덮이고 두 개의 돌 죽마로 걷는 극단적 기형을 갖고 태어난 올빼미입니다. Moon Studios 아트 디렉터 제레미 그리튼이 "돌처럼 굳은 날개를 죽마처럼 짚고 걷는 석화된 올빼미"라는 비주얼 콘셉트를 먼저 구상했고, 이 캐릭터 없이는 속편의 스토리 자체가 존재하지 않았을 것이라는 서술이 확인됩니다 — 적대 캐릭터의 비주얼 디자인이 서사보다 먼저 나온 사례입니다. [[29]](#ref-29)

슈리크 관련 시퀀스도 단계가 나뉩니다:

| 시퀀스 | 규칙 | 세부 진행 |
| :--- | :--- | :--- |
| 조용한 숲(Silent Woods) 최초 조우 | **순수 규칙 세트 B(시선 회피형)** | 짧은 플랫포밍 추격이며, 멈춰서 슈리크로부터 숨어야 하는 지점들이 있고 한 곳이라도 놓치면 즉사 — 쿠로의 중반부 은신 시퀀스와 구조적으로 동일함. [[30]](#ref-30) |
| 최종 보스전 중 추격 단계 | **제3의 하위 유형(패턴 암기형 전투-추격)** | 슈리크 체력의 1/3을 깎으면 일련의 플랫포밍 챌린지를 통한 추격이 시작되며, 특정 타이밍에 공격이 들어오므로 플레이어는 패턴을 암기해 피해야 함 — 순수 환경 탈출도 순수 은신도 아닌, 보스전에 내장된 추격 형태. [[31]](#ref-31) |

<div class="callout">
<p><strong>두 가지 시사점</strong>: ① 조용한 숲 시퀀스가 쿠로의 은신 시퀀스와 구조적으로 동일하다는 점은, "시선 회피형" 패턴이 쿠로 한 편에 국한된 우연이 아니라 <b>Moon Studios가 두 작품에 걸쳐 반복 검증한 패턴</b>임을 보여줍니다 — 규칙 세트 B 채택의 신뢰도를 더 높이는 근거입니다. ② 보스전 추격 단계는 기존 규칙 세트 A/B 어느 쪽에도 깔끔히 들어맞지 않는 <b>제3의 하위 유형 후보</b>입니다. 이 기획에 정식 도입할지는 8장 오픈 이슈로 남깁니다.</p>
</div>

**연속 도주형의 세부 설계 기법**(Game Developer 자료 기반 [[17]](#ref-17)):
- **프리뷰 기법**: 추격이 시작되기 전에 플레이어가 해당 환경을 미리 경험하게 해, 실제 추격 중에는 낯선 지형이 아니라 위협 자체에 집중하게 함.
- **위험-보상 구조**: 문을 막거나 되돌아가는 선택지를 제공해, 위험을 감수하면 더 많은 시간을 벌 수 있게 함.
- **완전 선형이 기본이나 부분 분기 가능**: 두 경로를 제시하되 하나로 수렴시켜, 스트레스는 유지하면서 막다른 길로 인한 실패는 최소화.
- **숙련도 기반 시간 변주**: 슈퍼 메트로이드는 샤인스파크 같은 고급 기술로 탈출 구간을 단축할 수 있는 여지를 미리 레벨에 마련해 둬, "정속 강제 스크롤"이 아니라 숙련도에 따라 여유 시간이 달라지는 설계를 보여줍니다. [[18]](#ref-18)
- **적응형 페이싱**: 긴소나무 탈출의 차오르는 물은 정속이 아니라 플레이어가 느리게 움직이면 함께 느려짐 — 위협의 속도를 플레이어 자신의 이동 속도에 연동시켜, 극한의 반사신경을 요구하는 대신 짧은 판단 시간을 확보해 줍니다. [[32]](#ref-32)
- **난이도별 체크포인트 대응(반면교사의 실제 개선 사례)**: 긴소나무 탈출은 오리지널판·Normal 이상 난이도에서 실패 시 구간 전체를 재시작해야 했으나, Definitive Edition의 Easy 난이도에는 체크포인트가 추가되었습니다 — 이는 개발사가 트라이얼 앤 에러 비판에 실제로 대응한 사례이며, 이 기획이 채택한 "구간별 체크포인트" 원칙(위 반면교사 문단)이 사후 검증된 해법임을 뒷받침합니다. [[33]](#ref-33)

**시선 회피형의 세부 설계 기법**(스텔스 게임 디자인 이론 기반 [[19]](#ref-19)[[20]](#ref-20)):
- **탐지 아이코노그래피**: 시야콘·소음 반경·경계 상태를 명확한 시각 기호로 전달해, 플레이어가 즉시 계획을 수정할 수 있게 함.
- **예고(telegraph)와 발각 시 구제**: 리틀 나이트메어의 추격자는 행동 패턴이 예측 가능하고 위험은 애니메이션·음악으로 충분히 예고되며, 발각되어도 즉사가 아니라 도망치거나 숨어서 벗어날 기회가 주어짐 — 이는 규칙 세트 B의 "정지가 죽음이 아니라 전략"이라는 설계와 정확히 일치합니다.
- **시야콘 정밀도의 선택**: 일부 게임은 탐지 가능한 정확한 범위를 그대로 보여주지만, 일부는 근사치로만 표시해 시야콘 밖에서도 발각될 수 있게 하는 난이도 조절 변형이 존재함.

### 7.3 아키텍처 — 부모 시퀀스 상태 + 규칙 세트 플러그인

완전히 별개인 시스템 두 벌을 새로 만들기보다, 공통 부모 상태 아래 규칙 세트만 다르게 꽂는 구조를 권장합니다. 7.2.1절의 마운트 호루 사례처럼 두 규칙 세트가 한 시퀀스 안에서 동시에 필요할 수 있으므로, **단일 선택(enum)이 아니라 동시에 켤 수 있는 플래그 조합**으로 설계합니다.

- **부모 상태(시퀀스 모드 공통)**: 탐험 UI·백트래킹 비활성화, 체크포인트를 시퀀스 전용(구간별)으로 전환, 2.1절의 카메라 리그가 제어권을 가져감(도주형은 강제 트래킹, 회피형은 위협의 시야콘을 화면에 읽히게 하는 프레이밍).
- **규칙 세트 A(연속 도주형)**: 강제 스크롤/전진, 환경 접촉 즉사 판정, 전투 시스템 비활성화.
- **규칙 세트 B(시선 회피형)**: 탐지 게이지 또는 시야콘 판정, 은신 유효 구역, 정지가 죽음이 아니라 전략이 되도록 판정 반전.
- **동시 적용**: A와 B를 동시에 켜면 "강제 전진 + 탐지 시 즉사"가 함께 작동하는 마운트 호루형 시퀀스가 됩니다.

이 구조는 4장에서 설계한 "감정 태그" 데이터 모델과 같은 사고방식입니다 — 시퀀스 진입 시 "이 구간은 규칙 세트 A" "이 구간은 규칙 세트 B"라는 설정을 지정해, 같은 시퀀스 모드 프레임워크가 재생 시점에 다른 규칙으로 동작하게 만듭니다. 다만 2.4.1절에서 바로잡았듯, 이 규칙 세트 설정은 연출 데이터(`CinematicSequence`)가 아니라 별도의 게임 로직 리소스(`SequenceModeConfig`)에 둡니다 — 연출과 판정 로직을 뒤섞지 않기 위해서입니다. 2.2절의 연출 스크립트 경로(플레이 없이 연출 데이터를 직접 작성하는 경로)가 추격 시퀀스의 `CinematicSequence` 저작에 그대로 쓰일 수 있습니다.

<div class="callout">
<p><strong>범위 표시</strong>: 이 절은 "부모 상태 + 규칙 세트 플러그인"이라는 아키텍처 방향까지만 정리한 것이며, 탐지 판정의 구체적 수치(시야콘 각도·유예 시간 등), 규칙 세트 A/B 각각의 정확한 데이터 스키마, 추격 시퀀스를 몇 개·어느 위치에 배치할지는 아직 설계되지 않았습니다. 8장 오픈 이슈로 남겨둡니다.</p>
</div>

### 7.4 쇼츠 영상 연출 구조와의 연계

이 기획의 원래 출발점(1장)은 쇼츠 연출용 무대였습니다. 7.1~7.3절에서 설계한 두 레벨 디자인 모드가 실제로 쇼츠 연출에도 유효한지 점검합니다(원문: `raw/20260930_shorts_vertical_video_format_research_raw.txt`).

#### 7.4.1 게이팅 탐험보다 추격 시퀀스가 쇼츠에 구조적으로 유리한 이유

게이팅 탐험 모드(7.1절)는 느린 발견·백트래킹이 본질이라 15~60초짜리 완결된 훅-클라이맥스-해소 구조를 만들기 어렵습니다. 반면 **스크립트 시퀀스 모드(7.2절)는 이미 "위협 등장 → 고조 → 해소"라는 쇼츠에 필요한 미니 아크를 내장하고 있습니다** — 예를 들어 7.2.1절의 폐허 탈출은 "은신 → 발각 위기 → 바위가 쿠로를 가로막으며 해소"라는 자기완결적 구조 그 자체입니다. 즉 추격 시퀀스는 추가 편집 없이도 쇼츠 소재로 거의 그대로 쓸 수 있는 형태이며, 이는 이 기획이 메트로이드배니아이면서도 추격 시퀀스를 정식 설계 대상으로 승격시킨 결정(1장)의 타당성을 재확인해 줍니다.

#### 7.4.2 세로 프레이밍 프로파일

유튜브 쇼츠 공식 규격은 9:16(1080×1920)이며, 스마트폰 사용자의 94% 이상이 세로로 시청한다는 조사가 확인됩니다. [[35]](#ref-35) 게임 본편은 가로(16:9) 화면을 전제하므로, 2.1절의 카메라 리그에는 **세로 프레이밍 프로파일**을 별도로 추가해야 합니다.

- 가로→세로 변환 기법은 크게 세 갈래(단순 크롭, 서브젝트 트래킹 리프레이밍, 블러 배경 패딩)로 확인되며, 이 중 **서브젝트 트래킹 리프레이밍**(피사체를 계속 추적해 세로 프레임을 재구성)이 가장 자연스러운 결과를 낸다고 확인됩니다. [[36]](#ref-36) 2.1절의 카메라 리그는 이미 피사체(캐릭터·위협)를 추적하는 기능을 갖고 있으므로, 별도 AI 리프레이밍 툴 없이 세로 프로파일에서도 동일한 추적 로직을 재사용할 수 있습니다.
- 게임 클립에서는 핵심 액션(캐릭터, 위협, 판정 지점)을 화면 **중앙 밴드**에 배치해야 한다는 원칙이 확인됩니다 — 플랫폼 UI가 화면 상·하단을 가리기 때문입니다. [[36]](#ref-36) 규칙 세트 B(시선 회피형)의 시야콘처럼 화면 주변부에 배치되기 쉬운 요소는, 세로 프로파일에서 별도로 중앙 쪽으로 재배치하는 로직이 필요합니다.

#### 7.4.3 연출 데이터의 하이라이트 트림 마커

2.2절의 "레코더 경로"로 채집한 연출 데이터에 **하이라이트 인/아웃 포인트**(쇼츠로 잘라낼 구간의 시작·끝 타임코드)를 메타데이터로 함께 저장하는 것을 권장합니다. 처음 3초 안에 훅이 성립해야 한다는 원칙 [[35]](#ref-35)을 고려하면, 추격 시퀀스 전체(수 분)를 그대로 내보내는 대신 "위협이 처음 화면에 들어오는 순간"부터 인 포인트를 잡는 것이 유리합니다.

- 게임 클립 특화 자료는 20~40초를 완주율 확보에 적합한 길이로 권장하며, "아이디어에 맞는 최단 길이를 선택하라"는 원칙(억지로 늘리면 리텐션이 오히려 떨어짐)도 확인됩니다. [[37]](#ref-37) 규칙 세트 A(연속 도주형)·B(시선 회피형) 각각의 "표준 지속 시간"을 이 범위에 맞춰 설계하면, 게임 본편용 시퀀스를 쇼츠용으로 재트림하는 수고를 줄일 수 있습니다.

#### 7.4.4 게이팅 탐험의 "연출 가능 순간" 태깅

7.4.1절의 한계에도 불구하고, 게이팅 탐험 안에도 쇼츠로 쓸 만한 짧은 완결 순간이 존재합니다: 새 능력 획득, 능력으로 새 경로가 열리는 순간(게이트 개방), 숨겨진 방 발견. 이런 순간은 주변의 느린 탐험과 분리해 **개별 "연출 가능 순간(cinematic beat)"으로 태깅**하고, 각각에 7.4.2절의 세로 프레이밍과 짧은 자체 완결 연출(카메라 줌인 → 이펙트 → 감정표현)을 미리 붙여두는 것을 권장합니다. 이는 4장의 "감정 태그"·7.3절의 "규칙 세트 태그"와 같은 데이터 모델 패턴이며, 별도 시스템이 아니라 기존 태깅 구조의 세 번째 용례로 추가하는 것입니다.

<div class="callout">
<p><strong>범위 표시</strong>: 이 절은 원칙과 방향(세로 프레이밍 재사용, 하이라이트 트림 메타데이터, 연출 가능 순간 태깅)만 정리했으며, 구체적인 트림 규칙·태깅 UI·세로 프로파일의 수치(예: 시야콘 재배치 반경)는 아직 설계되지 않았습니다. 8장 오픈 이슈로 남겨둡니다.</p>
</div>

### 7.5 일반(가로형 롱폼) 유튜브 영상 연출 구조와의 연계

쇼츠뿐 아니라 일반 가로형 롱폼 유튜브 영상에도 이 구조가 유효한지 점검합니다(원문: `raw/20260930_longform_youtube_video_structure_research_raw.txt`). 결론부터 말하면, **롱폼은 쇼츠와 요구사항이 상당 부분 반대입니다** — 쇼츠에서 약점이었던 게이팅 탐험이 롱폼에서는 오히려 강점이 됩니다.

#### 7.5.1 게이팅 탐험이 롱폼에서는 약점이 아니라 강점인 이유

게임 트레일러 편집 전문 자료는 "지나치게 시네마틱한 연출에 치우치면 실제 플레이 경험을 오도할 수 있고, 반대로 순수 게임플레이 릴은 흥미가 떨어질 수 있다 — 가장 뛰어난 트레일러는 시네마틱한 페이싱과 진짜 게임 메커닉을 결합한다"고 밝힙니다. [[38]](#ref-38) 즉 롱폼·트레일러에서는 **탐험(느린 빌드업, 월드 노출)과 추격 시퀀스(빠른 액션, 고조)를 의도적으로 배합**하는 것이 업계 권장 사항입니다 — 7.4.1절에서 확인한 "쇼츠는 탐험에 불리"라는 결론과 정확히 반대입니다. 리텐션 설계 원칙도 "2~4분마다의 챕터별 미니 페이오프"를 권장하므로 [[39]](#ref-39), 게이팅 탐험(빌드업 구간) 뒤에 추격 시퀀스(페이오프 구간)를 배치하는 교대 리듬이 롱폼 페이싱 설계와 자연스럽게 맞아떨어집니다.

#### 7.5.2 가로 네이티브 — 별도 프로파일 불필요

6장에서 이미 게임 본편을 16:9 가로로 설계했으므로, 롱폼 유튜브는 7.4.2절과 달리 **카메라 리그(2.1절)의 기본 프로파일을 그대로 쓸 수 있습니다** — 세로 프레이밍 프로파일 같은 추가 작업이 필요 없는, 원래 이 기획의 네이티브 포맷입니다.

#### 7.5.3 챕터 마커 — "연출 가능 순간" 태그의 재사용

1시간 분량 영상은 10~15개 챕터(평균 4~6분 간격)가 적절하며, 챕터가 없는 롱폼 영상은 이탈률이 40~60% 더 높다는 조사가 확인됩니다. [[39]](#ref-39) 7.4.4절에서 설계한 "연출 가능 순간" 태그(능력 획득, 게이트 개방, 비밀 발견 등)를 **유튜브 챕터 타임스탬프로 그대로 재사용**할 수 있습니다 — 감정 태그·규칙 세트 태그·하이라이트 트림 마커에 이은 같은 데이터 모델의 네 번째 용례입니다.

#### 7.5.4 트레일러 구조를 연출 스크립트 경로로 저작

게임 트레일러의 표준 구조는 훅(0~5초) → 빌드(5~30초, 기능·월드 다양성 노출) → 코어 루프 → 고조 → 엔드카드로 확인됩니다. [[38]](#ref-38)[[40]](#ref-40) 2.2절의 "연출 스크립트 경로"(플레이 없이 연출 데이터를 직접 작성하는 경로)로, 여러 게이팅 탐험 구간과 여러 추격 시퀀스의 하이라이트를 이 구조에 맞춰 잘라 붙인 별도의 요약 트레일러를 저작할 수 있습니다 — 실제 플레이 세션 녹화와는 별개로, 순수 편집 결과물로서 트레일러 한 편을 "연출"할 수 있다는 뜻입니다.

#### 7.5.5 쇼츠 대 롱폼 요구사항 대조

| 항목 | 7.4절 쇼츠 | 7.5절 롱폼 |
| :--- | :--- | :--- |
| 화면비 | 9:16(별도 프로파일 필요) | 16:9(기본 프로파일 그대로) |
| 게이팅 탐험의 역할 | 구조적 약점(제외 또는 짧은 비트로만 추출) | 강점(빌드업 구간으로 적극 활용) |
| 길이 | 20~40초(짧을수록 유리) | 15~25분(챕터로 탐색성 확보) |

<p><strong>범위 표시</strong>: 이 절도 방향(가로 네이티브 재사용, 챕터 태그 재사용, 트레일러 구조 저작)까지만 정리했으며, 실제 챕터 개수·트레일러 편집 순서 등 구체적 콘텐츠 기획은 아직 이루어지지 않았습니다. 8장 오픈 이슈로 남겨둡니다.</p>

## 8. 미확정 설계 항목(오픈 이슈)
*Open Design Decisions*

다음 항목은 이번 논의에서 언급되지 않았으며, 근거 없이 임의로 확정하지 않고 목록으로만 남깁니다.

- **팀 규모/개발 리소스**: 1인 개발인지 협업인지에 따라 4장의 감정표현 구현 방식 우선순위가 달라짐.
- **게이팅 능력 목록·순서**: 2장에서 게이팅이 정식 설계 대상으로 승격되었으나, 구체적 능력 목록·게이팅 순서는 아직 없음(`metroidvania_mechanics_and_level_design.html`의 능력 게이팅·폼시프팅 이론을 참고해 다음 단계에서 설계 필요).
- **추격 시퀀스 세부 규칙**: 7.3절의 규칙 세트 A/B 데이터 스키마(플래그 조합 포함), 탐지 판정 수치, 시퀀스 배치 수·위치가 아직 미정. 다만 7.2.1절에서 도출한 "예고 없는 즉사 함정 금지"·"구간별 체크포인트" 두 원칙은 설계 지침으로 채택 확정.
- **규칙 세트 C(패턴 암기형 전투-추격) 도입 여부**: 7.2.2절에서 발견한 슈리크 보스전 추격(공격 패턴 암기 기반)을 이 기획에 별도 규칙 세트로 도입할지, 아니면 4장의 전투 시스템(아직 미정)이 확정된 뒤 판단할지 미결정.
- **쇼츠 연출 연계 세부 사항**: 7.4절에서 방향(세로 프레이밍 재사용, 하이라이트 트림 메타데이터, 연출 가능 순간 태깅)만 정리했으며, 트림 규칙·태깅 UI·세로 프로파일의 구체적 수치(시야콘 재배치 반경 등)는 아직 설계되지 않음.
- **롱폼 연출 연계 세부 사항**: 7.5절에서 방향(가로 네이티브 재사용, 챕터 태그 재사용, 트레일러 구조 저작)만 정리했으며, 실제 챕터 개수·트레일러 편집 순서 등 구체적 콘텐츠 기획은 아직 이루어지지 않음.
- **연출 스크립트 데이터 포맷 세부 설계**: 2.4절에서 리소스 이원화·포맷 매핑·로컬라이제이션 키·델타 인코딩이라는 방향만 정리했으며, `CinematicSequence`/`SequenceModeConfig`의 정확한 필드 스키마, `Animation` 트랙·메서드 이름 명세, `CinematicPlayer` 추상화 인터페이스, 포맷 버저닝은 아직 설계되지 않음.

## 9. 용어 정리 및 정의
*Terminology & Definitions*

| 용어 | 정의 |
| :--- | :--- |
| **연출 라이브러리** | **Cinematic Direction Library**. 캐릭터 위치·감정·대사·카메라를 시간축 데이터로 기록·재생하는, 게임 로직과 분리된 계층. 본 기획의 핵심 아키텍처. |
| **레코더 경로** | **Recorder Path**. 실제 플레이 세션의 상태를 그대로 채집해 연출 자산으로 재현하는 진입 경로. |
| **연출 스크립트 경로** | **Scripted Path**. 플레이 없이 연출 데이터를 직접 작성해 장면을 구성하는 진입 경로. |
| **CinematicSequence** | 순수 연출 데이터(위치·애니메이션·감정 태그·대사·카메라 파라미터)만 담는 리소스. 게임 로직(규칙 세트)은 포함하지 않음. 2.4.1절 참조. |
| **SequenceModeConfig** | 규칙 세트 A/B/C 플래그·탐지 판정 수치 등 순수 게임 로직만 담는 리소스. `CinematicSequence`와 분리되어 참조만 됨. 2.4.1절 참조. |
| **CinematicPlayer** | `Animation`(연출 스크립트 경로) 및 커스텀 `CinematicSequence`(레코더 경로) 두 포맷을 공통 인터페이스로 추상화해 재생하는 노드. 2.4.2절 참조. |
| **델타 인코딩** | 레코더 경로에서 매 프레임이 아니라 상태가 실제로 바뀐 시점에만 이벤트를 기록하는 방식. 2.4.4절 참조. |
| **감정 태그** | **Emotion Tag**. 캐릭터의 표정·포즈·대사풍선 형태를 동시에 구동하는 공통 데이터 키. |
| **지방세력가** | 귀족은 아니나 양인보다 문화·예술적 혜택을 누리는 호화 가문. 세계관 내 호칭은 **호장(戶長)**. 역사적 원형은 별도 문서 [고려 호족·향리와 지방세력가 호칭 고증](goryeo_hojok_hyangni_terminology.html) 참조. |
| **문벌** | **Munbeol**(門閥). 세계관 내 중앙관료의 정식 호칭. 고려 전기 중앙 정계를 장악한 가문·관료 집단. "귀족" 표현은 학계 귀족제/관료제 논쟁과 세습 작위 부재 학설을 반영해 배제(2015 개정 교과서 표기와 일치). 대중적 별칭은 양반(兩班, 원래 문반·무반을 합친 관제 용어). |
| **외관** | **Oegwan**(外官). 세계관 내 지방관료의 호칭. 중앙 조정이 지방에 파견한 관료의 총칭이며, 대표 직위는 목사(牧使, 8목·12목 정3품). |
| **능력 게이팅** | **Ability Gating**. 메트로이드배니아 장르의 핵심 진행 메커니즘으로, 특정 능력 획득 전까지 맵의 일부 경로를 봉쇄하는 설계. 상세는 `metroidvania_mechanics_and_level_design.html` 참조. |
| **Godot 엔진** | 이 프로젝트의 채택 기술 스택. 텍스트 기반 씬(`.tscn`)·리소스(`.tres`) 포맷과 내장 `TileMap` 에디터가 채택 결정의 핵심 근거. 상세는 5장 참조. |
| **HD-2D** | 도트 스프라이트와 3D 환경·동적 조명·피사계심도를 결합한 렌더링 방식. 스퀘어에닉스가 옥토패스 트래블러에서 명명. 6.2절 참조. |
| **블룸** | **Bloom**. 밝은 픽셀을 추출해 블러 처리 후 원본에 가산 합성하는 후처리 효과. Godot은 `WorldEnvironment`의 Glow 기능으로 내장 지원. |
| **색수차** | **Chromatic Aberration**. R/G/B 채널을 화면 중심에서 멀어질수록 다른 방향으로 어긋나게 샘플링하는 후처리 효과. |
| **선택적 아웃라인** | **Selective Outlining(Sel-Out)**. 배경과 맞닿는 그림자 쪽만 진한 선을 넣고 빛 받는 쪽은 밝은 내부색을 살리는 아웃라인 기법. 6.3절 참조. |
| **색상 맞춤 아웃라인** | **Shade-Matched Outline**. 순수 검은색 대신 칠해진 색과 같은 색상군의 더 어두운 톤을 테두리로 쓰는 아웃라인 기법. 이 프로젝트의 1차 권장안. |
| **게이팅 탐험 모드** | 표준 메트로이드배니아 규칙으로 플레이어가 자유롭게 되돌아다니는 레벨 디자인 모드. 7.1절 참조. |
| **스크립트 시퀀스 모드** | 연출 라이브러리가 카메라·판정을 강제로 넘겨받는 레벨 디자인 모드(추격전 등). 게이팅 탐험 모드와 대비되는 개념. 7.2~7.3절 참조. |
| **연속 도주형** | 스크립트 시퀀스 모드의 규칙 세트 A. 강제 전진/스크롤, 환경 접촉 즉사, 정지가 곧 죽음인 추격 시퀀스. 《슈퍼 메트로이드》 최종 탈출 시퀀스, 《오리 앤 더 블라인드 포레스트》 마운트 호루 탈출이 대표 사례. |
| **시선 회피형** | 스크립트 시퀀스 모드의 규칙 세트 B. 탐지(시야콘) 판정 기반이며 정지·은신이 유효한 전략인 추격 시퀀스. 리틀 나이트메어의 거대 추격자 회피 구간이 대표 사례. |
| **스크립트 시퀀스** | **Scripted Sequence**. 플레이어의 위치·행동으로 트리거되어 게임 엔진 안에서 재생되는 미리 정의된 사건 계열. 이 기획의 "스크립트 시퀀스 모드" 명칭의 원어 근거. |
| **추격 시퀀스** | **Chase Sequence**. 적의 추격과 대안 경로 부재로 긴장을 조성하는, 대체로 선형적인 레벨. Game Developer(舊 Gamasutra)의 정의. |
| **시야콘** | **Vision Cone**. 적의 시야 범위를 도식화해 플레이어가 관찰·회피할 수 있게 하는 스텔스 메커닉. 1981년 《005》(세가)가 최초 도입. |
| **쿠로 시퀀스** | 《오리 앤 더 블라인드 포레스트》의 거대 부엉이 쿠로 관련 시퀀스. 중반부는 순수 시선 회피형, 후반부(마운트 호루)는 연속 도주형+시선 회피형이 중첩된 사례로, 이 기획의 "규칙 세트 동시 적용" 설계(7.3절)의 근거. 세이브 포인트 부재로 인한 트라이얼 앤 에러 비판의 반면교사 사례이기도 함. |
| **긴소나무 탈출** | 《오리 앤 더 블라인드 포레스트》의 "물 탈출" 시퀀스. 쿠로의 즉사 시야 판정이 섞이지 않은 순수 규칙 세트 A(연속 도주형) 사례. 위협 속도가 플레이어 이동 속도에 연동되는 "적응형 페이싱"과, Definitive Edition Easy 난이도의 체크포인트 추가(트라이얼 앤 에러 비판에 대한 개발사의 실제 대응)의 근거. |
| **세로 프레이밍 프로파일** | 카메라 리그(2.1절)에 추가되는 9:16 세로 출력 전용 설정. 서브젝트 트래킹 리프레이밍과 중앙 밴드 배치 원칙을 따름. 7.4.2절 참조. |
| **하이라이트 트림 마커** | 연출 데이터(2.2절 레코더 경로)에 함께 저장되는 쇼츠용 구간 인/아웃 타임코드 메타데이터. 7.4.3절 참조. |
| **연출 가능 순간** | **Cinematic Beat**. 게이팅 탐험 중 능력 획득·게이트 개방·비밀 발견처럼 짧게 완결되는 지점을 주변 탐험과 분리해 태깅한 것. 감정 태그·규칙 세트 태그와 같은 데이터 모델의 세 번째 용례. 쇼츠(7.4.4절)에서는 개별 클립으로, 롱폼(7.5.3절)에서는 유튜브 챕터 타임스탬프로 재사용됨. |
| **슈리크 시퀀스** | 《오리 앤 더 윌 오브 더 위습스》의 거대 부엉이 슈리크 관련 시퀀스. 쿠로와는 다른 작품·다른 캐릭터. 조용한 숲 조우는 쿠로와 동일한 시선 회피형 패턴(규칙 세트 B의 반복 검증 근거), 보스전 추격은 패턴 암기형 전투-추격(규칙 세트 C 후보)이라는 새 유형을 시사. |
